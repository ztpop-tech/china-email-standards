# M3AAWG 邮件流量分析导论

## 概述

流量分析（Traffic Analysis）是一种不依赖解密邮件内容，仅通过分析已加密通信的外部特征——如发件人、收件人、时间戳、消息大小、通信频率和流量模式——来获取情报的攻击手段。即使消息通过了 PGP/GPG 或 S/MIME 的端到端加密，不可阅读其正文，攻击者仍然可以从元数据中推测出大量信息。

对于邮件安全运维人员而言，理解流量分析不仅是从"防守者"的角度认知威胁，更是一种强大的"溯源和分析"工具：通过分析邮件流量的统计特征，可以识别出垃圾邮件爆发、僵尸网络活动、账号被盗后的异常行为模式，以及钓鱼攻击的传播路径。

M3AAWG（反恶意软件消息传递及移动反滥用工作组）于 2016 年 6 月发布了本篇《Introduction to Traffic Analysis》，旨在向通信行业介绍这一风险/攻击场景。本文在完整译介原文的基础上，增加了针对国内大邮件系统流量分析运维实践的补充内容。

## 1. 引言（Introduction）

防范无孔不入的监控和加密的推广使用，一直是通信行业的重要关注点。M3AAWG 此前已发布了一系列初步建议，包括部署 TLS[1]、缓解中间人攻击[2]以及使用前向保密（Forward Secrecy）保护数据[3]，以帮助通信社区更好地保护邮件在传输中的安全。现在，M3AAWG 希望将业界注意力引向另一种风险——被称为**流量分析（Traffic Analysis）**的攻击形式。

本文阐述流量分析的核心特征，讨论规避流量分析的可能方法，并分析部署防范措施的利弊。

## 2. 理解邮件与网络流量中的流量分析

### 2.1 邮件消息层面的可见性

使用 PGP/GPG（GNU Privacy Guard）[4] 或 S/MIME[5] 加密的消息内容通常对窃听具有高度的抵抗力。即使第三方获取了加密邮件的副本，也不太可能解密阅读。然而，即使消息通过端到端加密得到了完美保护，**仍然可能遭受流量分析攻击**。

为理解这种差异，考虑以下邮件消息元素汇总表——这些是中间 SMTP 服务器在利用 TLS 传输消息时可见的邮件元素，以及它们在流量分析中的脆弱性：

邮件消息元素在流量分析中的可见性

| 邮件消息元素 | 易受流量分析攻击？ |
| --- | --- |
| Return-Path: 头部 | 是 |
| Received: 头部 | 是 |
| From: 头部 | 是 |
| To: 头部 | 是 |
| CC: 头部 | 是 |
| Date: 头部 | 是 |
| Subject: 头部 | 是 |
| Message-ID: 头部 | 是 |
| 任何/所有其他头部 | 是 |
| 消息大小 | 是 |
| 消息接收时间 | 是 |
| 消息使用的加密方式（可见） | 是 |
| 消息内容（假定可能或已加密） | 否 |

在流量分析攻击中，关注点不在于内容本身，而在于消息头部及其他与消息或通信过程相关联的**外部可见特征**。上表列出的这些元素，在中间 SMTP 服务器（使用 TLS 传输消息）上都是可见的，因此也都能被用于流量分析。

### 2.2 网络流量层面的可见性

同样，针对网络流量（而非特指邮件流量）的流量分析，通常依赖 NetFlow[6] 或等效协议提供的数据。如下表所示，这些流数据同样易受流量分析攻击：

网络流量流在流量分析中的可见性

| 网络流量流数据 | 易受流量分析攻击？ |
| --- | --- |
| 流中的包数 | 是 |
| 流中的字节数 | 是 |
| 开始/结束时间戳 | 是 |
| 源/目的 IP 地址 | 是 |
| 源/目的端口号 | 是 |
| IP 协议 | 是 |
| 服务类型值（ToS） | 是 |
| 标志位 | 是 |
| [其他] | 是 |
| 包内容 | 否 |

## 3. 流量分析如何工作（How Traffic Analysis Can Work）

表面上看，流量分析者无法访问消息内容似乎受到很大限制，但事实上，从非内容相关特征中可以挖掘出令人惊讶的大量信息。

### 3.1 源/目的分析（Source/Destination Analysis）

**示例一：**想象一位在敏感岗位工作的政府雇员，向一名调查记者或敌对外国情报机构的代表发送了一封加密消息。一旦该消息被注意到，仅凭该雇员发过这样一条消息这一事实——无论加密消息实际内容是什么——就足以引发审查。标记该通信以便进一步检查，只需知道消息的源和目的即足矣。

**示例二：**再想象一个处理信用卡交易的企业管理系统。该系统的正常通信对象仅限订单接收网站和信用卡公司。如果分析者突然注意到该计算机与世界中某个陌生系统之间出现了加密连接，这通常会是一个**推定信号**——表明某系统可能已被入侵。

**示例三：**与僵尸网络命令与控制（C2）主机相关的分析。如果一台桌面系统突然开始与已知的 C2 主机通信，则强烈表明该桌面可能已被植入僵尸程序（这一过程有时称为将 C2 主机作为"手指指向工具"）。

**示例四：**所谓"寻呼器记录令"（Pen Register）和"追踪记录令"（Trap-and-Trace）[7] 是源/目的流量分析的司法实践范例。这些法令允许经司法授权的调查人员获取特定通信的源和目的信息，但不得获取通话内容。执法部门经常使用这些手段获取已知犯罪组织成员的联络号码，或识别与已知毒枭合作的中间人。

### 3.2 流量体量分析（Traffic Volumetric Analysis）

调查人员甚至可能不需要知道谁在和谁通信——只需知道通信量的多少。简单的流量体量变化本身就可能传达重要信息。

考虑分析人员监测进出敌对国家的加密军事通信：经过数月或数年的监测，分析人员会逐渐熟悉常规的基础流量——例如一个典型小型站点每天收发 400 至 500 条消息。分析人员知道这是该站点的正常基线。

然而，如果该国突然开始备战，流量水平就会增加——至少对于被调动的部队单位而言——因为指令正被发送出去指挥他们做好战斗准备。某些基地的流量可能会达到正常水平的四五倍。这种简单的体量变化，即使消息内容本身已加密且无法破译，也能被外部监测者轻易发现（这就是媒体中有时提及的"通讯量增加"现象）。由于部分基地流量增加而其他基地没有，分析者不仅知道有事情正在筹划，还知道**哪里**在筹划、**哪些部队**可能正在被调动。这是有价值的情报，即使他们看不到实际的消息内容。

反过来，如果正常流量水平突然降至零——即为了规避非加密传输带来的风险而实施"无线电静默"——这种下行变化本身同样是事态即将发生的重大指标。

### 3.3 序列分析（Sequence Analysis）

假设某站点运行了一个加密的邮件列表服务器。监测该服务器流量的外部分析者可能会看到：一条加密消息进入该服务器，然后不久，几乎同样大小的重新加密消息被发送到分布在不同站点的约三四十人。这一模式反复出现。

基于这一模式，分析者可以合理推断：这三四十人都是同一个加密邮件列表的成员，共同关注某个特定话题。例如，如果识别出的成员中有很大一部分已知参与了某个政治反对团体，那么一个合理的推断是：该列表的**所有**成员都与该反对团体有关——即使其中一些成员此前并不被如此认知。

### 3.4 推断分析（Inferential Analysis）

对多个独立事件（这些事件共同构成"流量"）进行关联分析，可以拼凑出一幅关于某个更大事件的全景图。考虑这样一个场景：某人的四十岁生日即将到来，而其配偶发现了来自帐篷租赁公司的邮件、来自 DJ 的收据以及来电显示上本地面包房的号码。这些独立的事件本身不直接表明某个行为，但将这些信息碎片拼在一起，就能揭示出举办惊喜生日派对的巨大可能性。

这种审查方式以及其他方法构成了流量分析的过程——即使通信内容被完全加密，也允许对通信进行分析。

## 4. 规避流量分析攻击（Avoiding Traffic Analysis Attacks）

有多种方法可以规避流量分析攻击。以下列举了几种常见策略，以帮助了解业界已经采取的部分对抗措施。

### 4.1 通过中间跳点解耦源和目的

这种方法力求避免将通信的发送者和接收者直接关联，而是通过多个中间跳点间接路由通信。这是匿名转发器（Anonymous Remailers）[8] 通常采用的方法。

### 4.2 将所有流量隧道至第三方

另一种应对方式是将所有流量从其实际源地址隧道传输至第三方出口节点——例如通过商业 VPN（虚拟专用网络）连接。VPN 提供商必须审慎选择，因为提供商通常既知道 VPN 购买者的身份，也可能知道通过 VPN 传输的流量内容。此外，网络流量分析者可以轻易检测到这种措施，相关机构也可能通过行政或技术手段加以阻止。但从技术角度看，本地流量分析者只能看到通往单一远程目的地的加密隧道流量；而远程流量分析者也只能看到流向隧道端点而非最终目的地的流量。

### 4.3 通过广播或发布方式解耦源和目的

这种方法力求消除发送者与接收者之间的直接连接，用广域发布替代定向投递。

一个简单的非在线示例：假设发送者 A 想与接收者 B 通信。A 可以写信寄给 B，但这会直接将二者关联——至少当这封信被注意到时如此。作为替代方案，A 可以将给 B 的通信内容以编码报纸分类广告的形式发布。

既然 A 通过广播机制（报纸）公开通信，第三方就不可能知道数十万报纸订阅者中 A 真正想和谁通信。A 与 B 之间的联系因此变得无法建立。

在线上环境中，在线发布消息的类似做法可见于 Usenet News。Usenet News 是一个去中心化的讨论平台，围绕数万个不同的新闻组（话题讨论区）组织。某一新闻组的参与者的帖子会自动通过服务器之间的新闻推送被"淹没"或"推送到"所有承载该新闻组的新闻服务器。这意味着在美国西海岸发布的帖子可以在几秒钟内传播到全球数千台新闻服务器。

一旦帖子被新闻服务器接收，只有每台本地服务器的管理员才能知道哪个用户正在阅读哪个新闻组。显然，将一条加密的个人消息全球广播到只需要一个人阅读、且只有一个人能解密的消息，是非常浪费的——但这确实在发生。以下是从 Usenet 新闻组 alt.anonymous.messages 中摘录的一条帖子示例：

Path: ks2ni12827igb.0!nntp.google.com!peer01.iad.highwinds-media.com!
news.highwinds-media.com!feed-me.highwinds-media.com!
usenet.blueworldhosting.com!feeder01.blueworldhosting.com!
news.mixmin.net!.POSTED!not-for-mail
From: "Nobody" <nor...@mixnym.net>

任何人都能看到消息，但由于它经过 PGP 加密，只有持有相应私钥的人可以解密阅读。而且由于它是作为新闻组的一部分发送到全球而非直接来自发件人发往收件人，没有人知道是谁发出了消息、又是谁收取该消息。这种方法相当强大，但并不完美——参见"De-anonymizing Alt.Anonymous.Messages"[9] 中的讨论。

### 4.4 恒定流量通道（Constant Volume Traffic Channels）

为规避流量体量分析攻击，站点可以安排交换**恒定体量的加密流量**——在没有真实消息传输时发送可忽略的随机内容。由于流量体量不变，基于体量的分析方法就失去了作用。恒定流量通道还有一个优势：可以证明特定通信路径始终在线且可用。

这种方法的缺点是通信带宽被永久占用，造成容量浪费。此外，这种方法也会让双方之间持续的重要连接变得难以隐藏。最后，发送恒定加密流量流也会增加可供密码分析者攻击的加密文本语料。

另一种变体是模拟流量突发——模拟出类似真实事件发生时的流量模式。如果有足够多的虚假警报，那么真实流量增长就可能被误认为是又一次模拟突发。

## 5. 规避流量分析的后果（Consequences of Attempts to Evade Traffic Analysis）

为规避流量分析而采取的措施，往往会使特定提供商的流量从常规网络流量中**脱颖而出**。原本可能被忽略的流量现在反而更容易受到审查。

由于通过匿名转发器等反流量分析通道发送的流量无法溯源，垃圾邮件发送者可能试图滥用此类站点投递消息。匿名转发器的运营者通常会对滥用行为进行抵御，但他们治理滥用的能力并不完美。因此，部分接收系统可能会从策略上直接阻止所有来自已知匿名转发器的流量。

匿名转发器可能会故意引入消息重传延迟，以解耦网络可见的输入流量与输出流量的关联。这种额外延迟通常不构成问题，但在某些时间敏感场景下可能会造成困扰。

许多反流量分析方案依赖通过中间节点转发流量。如果未加密消息通过一个或多个不可信的中间节点转发，这些节点就可能窃听流量。不可信的中间节点也可以丢弃其受托重传的流量，从而干扰消息投递。

反流量分析措施可能导致流量被路由到海外，这可能带来以下后果：

* 原本因法定豁免而免于分析的国内流量可能因此受到审查，因为流量的国内源被掩盖后，流量呈现国际来源特征；
* 流量可能需要同时遵守远程站点的法律和监管制度；
* 搜索引擎及其他资源可能基于使用的隧道端点进行不当本地化（例如，VPN 终止于德国，则用户可能看到德语而非英语的内容）；
* 间接路由流量会引入不可避免的实际延迟，因为流量需要经过更长的物理距离到达/来自远程隧道端点；
* 旨在抑制流量分析的商业解决方案（例如商业 VPN 服务）在大规模采购时可能成本高昂。

## 6. 结论（Conclusion）

大多数用户对流量分析风险的认知有限，可能不太愿意采用对抗措施。某些对抗措施也可能无意中增加流量受到的审查程度。使流量更难以被分析是一项具有挑战性的工作——它需要设计网络、协议和运营层面标准的小组共同努力，也需要用户提高认知。这些长期目标可以从今天开始——在明确可靠之前，通过实验和部署逐步推进。流量分析可能是一个更专业化的领域，但 M3AAWG 希望业界认知到这一风险/攻击场景，并建议通信行业继续研究对抗措施以降低风险。

## 8. 国内场景补充：大邮件系统流量分析实践

M3AAWG 的原始报告主要面向国际市场和国际邮件基础设施。在国内环境下，大型邮件系统的流量分析面临着更加复杂的挑战。以下结合国内大邮件系统运维的实际情况，补充几条关键实践。

### 8.1 国内大邮件系统的流量特征

国内大型邮件系统（如运营商级邮件平台、政企邮件系统）通常具有以下流量特征：

* **用户基数大、流量集中：**单系统承载数千万乃至上亿用户，日处理邮件量可达数亿封。SMTP 入站/出站流量高度集中，对流量采集、存储和实时分析提出了极高的性能要求。
* **流量突发性强：**节假日促销邮件、政务通知发放、考试/报名集中期等场景下，入站和出站流量可在短时间内飙升数十倍。流量分析系统需要具备弹性扩展能力。
* **国内国际混合路由：**跨境邮件需经过国际邮件网关审查和安全过滤，导致邮件投递路径较国际邮件更长、中间节点更多，增加了流量分析的复杂度。
* **内容审查与合规要求：**国内邮件系统需要同时满足《网络安全法》《数据安全法》《个人信息保护法》及等保 2.0 等法规要求，流量分析不仅用于安全检测，还需承担日志留存、审计溯源等合规功能。
* **IPv6 接入占比持续上升：**随着国内 IPv6 大规模部署，邮件系统需要同时纳入 IPv4 和 IPv6 双栈流量的分析视角，避免因协议维度带来的盲区。

### 8.2 流量数据的采集方法

国内大邮件系统常见的流量数据采集方式包括：

* **MTA 日志采集：**通过 Postfix、TurboEx 或其他 MTA 的 syslog 或专用日志管道，实时采集每条消息的会话信息（源 IP、目标 IP、发件人/收件人域名、消息大小、连接时长、认证结果、TLS 协商结果等）。日志采集通常采用 Flume/Logstash/Filebeat 等方式汇总到统一的日志中心。
* **NetFlow/IPFIX 导出：**在网络出口和核心交换节点启用 NetFlow v9 或 IPFIX 协议，采集流级别的网络通信信息。对于大流量场景，可采用采样（Sampling）机制控制数据量。
* **SMTP 会话拦截：**在 SMTP 代理层或反垃圾网关层截取邮件会话的初步握手信息（HELO/EHLO、MAIL FROM、RCPT TO 阶段的域名和地址），用于构造实时流量指标。
* **HTTP API 上报：**对于云原生或分布式邮件系统，各模块通过内部 API 上报流量指标到监控中心，形成统一的流量数据池。

### 8.3 流量基线建立与异常检测

国内大邮件系统的流量基线建立通常采用以下方法：

* **多时间粒度基线：**分别建立分钟级、小时级、日级和周级基线。例如，对于出站流量，需要区分工作时段（9:00-18:00）和低谷时段（23:00-6:00），并考虑"周周期"规律——周一的出站量通常高于周六。
* **滑动窗口 + 指数加权移动平均（EWMA）：**使用 EWMA 计算实时流量的平滑值，并设置动态阈值（例如均值 ±3σ）。当实际流量超出阈值时触发告警。
* **季节性分解：**使用 STL（Seasonal-Trend decomposition using Loess）等算法将流量时序分解为趋势分量、季节分量和残差分量，从残差中识别异常——这种方法能较好地区分"业务增长带来的趋势性变化"与"攻击事件带来的突发性异常"。
* **多维度联合分析：**单一维度的流量异常（如总邮件量突增）可能有多种解释（促销活动、邮件批量发送、CC 攻击等）。需要结合来源 IP 分布、目标域名分布、消息大小分布、认证成功率等多维度指标进行联合判定。例如，如果出站量突增但 SMTP 认证成功率同步下降、来源 IP 集中在少数几个 ASN，则大概率是账号被盗后的垃圾邮件发送行为。

### 8.4 与 Spamtrap 数据的结合

M3AAWG 在另一份最佳实践《Spamtrap BCP》中详细讨论了 Spamtrap 的使用方法。在国内大邮件系统场景下，spamtrap 数据可与流量分析深度结合：

* **Spamtrap 命中作为已知恶意来源的标签：**当某个 IP 或发件域发送到 spamtrap 的数据被确认后，这些来源的流量特征（连接模式、消息频率、头部特征等）可以反向添加到流量分析模型中，用于识别该来源的其他变体流量。
* **Spamtrap 与流量基线的关联分析：**如果系统中发现 spamtrap 命中量突增，需要同时回看该时间段内整体入站流量的基线变化——是整体垃圾邮件都在增长，还是特定发件来源在定向攻击。这种关联分析能帮助区分"全行业性垃圾邮件爆发"与"针对本系统用户的定向攻击"。
* **本地 Spamtrap 池：**大邮件系统应部署自有 spamtrap 地址池，覆盖本系统的域名空间，以捕获针对本系统用户的定向垃圾邮件和钓鱼尝试。Spamtrap 地址的生成和轮换应自动化，避免被攻击者识别过滤。

### 8.5 可视化与告警

流量分析的数据最终需要转化为可行动的情报。国内大邮件系统通常使用以下可视化工具和策略：

* **Grafana + Prometheus/Elasticsearch 技术栈：**实时展示邮件流量的关键指标仪表盘，包括：入站/出站邮件量时序、SPF/DKIM/DMARC 认证通过率、Top 发件来源国家/地区、Top 收件域名、SMTP 错误码分布、连接延迟和队列深度等。
* **流量热力图：**以小时为横轴、日期为纵轴的热力图展示流量密度，能够直观呈现流量异常的时间窗口和周期性规律。
* **多级告警策略：**设置不同的告警级别。例如：单条连接超阈值 → Info 日志；连续 3 个时间窗口超阈值 → Warning 通知；单发件域出站量突增至日常 10 倍以上 → Critical 告警并自动触发限流或封禁。
* **告警抑制与降噪：**国内大系统面临的告警风暴问题尤其突出。需要实施基于"事件收敛"的告警策略——相同来源的多个异常合并为一条事件，经过人工或自动研判后再确定是否需要响应。

### 8.6 流量分析在零信任邮件体系中的定位

随着零信任架构在邮件安全领域的推广，流量分析的角色也在发生转变。在零信任邮件体系下：

* 每封邮件（无论来自内网还是外网）都需要经过认证、授权和持续评估；
* 流量分析不再局限于"入站检测恶意流量"，而是扩展为对**所有邮件流量行为**的持续监控和风险评估；
* 用户或设备的"正常流量行为基线"成为零信任判定的重要输入——当行为偏离基线时，执行逐步升级的安全措施（如加速过期、要求二次认证、限制敏感数据转发等）。

流量分析从被动防御走向主动风险评估，这是国内大型邮件系统未来发展的重要方向。
