## 一、引言

M3AAWG（消息、恶意软件与移动反滥用工作组）与 i2C（互联网基础设施联盟）共同为托管商、DNS 和域名注册服务商提供以下最佳实践，以支持 M3AAWG 减少各类消息发送及其他形式网络滥用的使命。本文旨在教育服务商如何更高效地利用自身资源对抗滥用行为。

托管服务商必须遵守这些要求，以避免行业及监管执法行动，并防范被施加额外监管的风险。服务商还应考虑加入相关联盟并遵守相应的自律监管倡议，例如由其他行业贸易协会制定的规范。托管服务商必须符合其上游网络服务商和适用地区政府法规的要求。（参见[附录二](#appendix2)。）

本文概述了行业最佳通用实践。本文认同并非所有托管服务商或举报机构都能实施全部实践，原因是网络基础设施的复杂性、公共政策的考量以及网络平台的可扩展性限制。

## 二、托管类型

各托管服务商提供的支持水平、设备配置及客户滥用问题的协助力度各不相同。

| 托管类型 | 硬件 | 操作系统 | 软件 | 滥用问题 |
| --- | --- | --- | --- | --- |
| 独立服务器 | 服务商 | 客户 | 客户 | 客户\* |
| 管理型托管 | 服务商 | 服务商 | 服务商 | 服务商或客户 |
| 代理商托管 | 服务商或客户 | 客户或客户的客户 | 客户或客户的客户 | 客户或客户的客户\* |
| 共享托管 | 服务商 | 服务商 | 服务商 | 服务商与客户 |
| 非管理型托管 | 服务商与客户\* | 客户 | 客户 | 客户\* |
| 虚拟私有服务器（VPS） | 服务商 | 服务商 | 客户 | 客户 |

\* 当客户拥有硬件时（如在托管环境中），硬件维护责任由托管服务商与客户共同承担。

### 各类托管组织形式定义

云托管（Cloud Hosting）
:   具备冗余机制的共享托管。

独立服务器托管（Dedicated Hosting）
:   托管服务商拥有并提供服务器、机房物理空间、网络连接、电力及物理安全。客户控制并维护服务器、操作系统、软件、管理及终端用户访问。托管公司提供仅分配给单一客户的专属服务器。客户通常拥有该服务器的管理员级访问权限。

托管服务商（Hosting Provider）
:   任何向终端用户提供在其不实际拥有的硬件上创建 Web 存在能力的实体。

管理型托管（Managed Hosting）
:   托管服务商拥有并提供服务器、操作系统、软件和/或技术支持。客户控制管理及终端用户访问权限。

代理商托管（Reseller Hosting）
:   托管公司向一个客户提供空间，该客户充当独立托管公司。商业安排可以是上述的非管理型或独立服务器托管。客户可以自行定位为托管服务商，并向其客户销售服务。代理商还可以向其他代理商转售，从而增加责任层级，导致滥用处理流程中的潜在延迟。

共享托管（Shared Hosting）
:   托管服务商拥有并提供服务器、机房物理空间、网络连接、电力、物理安全，以及操作系统和软件。服务商控制管理访问权限；客户控制终端用户访问。共享系统中的滥用问题需要服务商引导客户走向正确的解决方案。

非管理型托管（Unmanaged Hosting）
:   托管服务商提供机房物理空间、网络连接、电力及物理安全。客户拥有、控制并维护服务器、操作系统、软件、管理及终端用户访问权限。

虚拟私有服务器（VPS）
:   客户被分配一个虚拟服务器环境，通常拥有对该环境的管理员级控制权。在某些情况下，客户还可能拥有有保障的进程或硬件资源分配。托管服务商拥有并提供虚拟服务器环境和操作系统。客户控制管理及终端用户访问权限和软件。

## 三、滥用类型

以下是托管和云服务商中最常见的滥用类型列表。此列表并非完整无遗，且将不可避免地随时间变化。

垃圾邮件（出站）
:   垃圾邮件是指收件人明确表示不希望接收的任何电子邮件。服务商应确保客户遵循 M3AAWG 发件人最佳当前实践。托管服务商还应尽可能多地订阅相关反馈循环（FBL）报告（关于反馈循环的更多信息，见第五节）。

垃圾广告推广（托管重定向与载荷）
:   当托管服务商的终端用户委托第三方推广其 Web 存在时即发生垃圾广告推广。大多数垃圾邮件投诉是由于终端用户向潜在客户发送宣扬某些过度包装的产品或服务的电子邮件造成的。垃圾广告推广通过第三方进行。收到此类投诉的服务商很可能处于链路中——要么是电子邮件的发送方，要么是被推广网站的托管方。

钓鱼攻击（出站托管与入站凭证收集）
:   钓鱼攻击主要发生在终端用户账户被入侵时，几乎总是由于终端用户运行过时的脚本所致。钓鱼网站是一个伪装成合法公司（如美国银行或 PayPal）的欺诈性网站，诱骗个人输入机密信息。钓鱼者随后拥有所需的一切以盗取刚刚受骗者的钱财。

被篡改或涂改页面（托管客户端侧）
:   虽然钓鱼投诉通常归入此类，但并非所有被入侵账户都用于钓鱼。有些可能仅仅是遭涂改，终端用户数据被破坏或删除。黑客还经常注入恶意代码或上传机器人程序造成更多问题。第三方和执法机构分析这些事件，并提供修复被篡改站点的信息。大多数账户被入侵是由于终端用户过时的 CMS（内容管理系统）安装——如 Joomla 或 WordPress。

儿童性虐待材料（托管客户端侧）
:   关于此类问题的适当处理，参见 M3AAWG 儿童性虐待材料处置最佳实践。

版权和商标/知识产权问题（托管客户端侧）
:   关于美国在线版权法，参见美国版权局 DMCA 报告摘要。其他司法管辖区适用其他版权制度。

分布式拒绝服务攻击及其他出站恶意流量（托管放大、重定向、僵尸网络 C&C 主机）

恶意注册（打地鼠式多账户多平台注册）

## 四、预防

### 4.1 在客户造成问题之前进行审查

托管服务商的声誉受制于客户的最差实践。服务商必须具有某种类型的审查流程，以在恶意客户进行滥用活动之前主动识别他们。服务开通前的健全审查流程将帮助服务商区分真正的恶意行为者和仅仅需要正确在线行为指导的客户。客户审查对于维护良好声誉、降低成本和减少在线滥用至关重要。

### 4.2 要求客户保持软件更新

未能保持环境和软件/固件的及时更新是托管空间滥用的主要原因之一。客户协议应规定客户将尽最大努力使其系统保持更新。这包括：

* 操作系统/安装
* 插件
* 内容管理系统（CMS）
* 主题
* 硬件/固件

协议应明确过时的软件可能违反与客户的合同，因为它可能对其自身环境和他人的安全造成风险。在可能的情况下，客户应为其环境启用自动软件更新。

### 4.3 防止滥用者成为客户

在制定预防计划时，必须优先考虑在意图进行滥用活动的各方进入托管商系统之前阻止他们。以下做法有助于防止欺诈账户进入托管系统：

* 对新账户实施预授权。
* 对可疑账户进行人工联系。
* 保留先前被终止的欺诈账户记录。
* 对新账户设置限制，只有在有可信客户需要时才予以放宽。
* 如可能，引入欺诈评分系统，自动拒绝低于指定阈值的潜在账户。
* 为销售团队提供特定的询问问题和需警惕的潜在账户危险信号表述，以帮助识别潜在的欺诈。

### 4.4 对面向客户的员工进行安全意识培训

面向客户的团队——如支持、销售和市场——通常不面对滥用或安全团队日常面临的大部分挑战。培训使这些团队了解何时告诉客户或潜在客户，他们的做法不符合其所处系统或试图配置环境的可接受使用政策（AUP）和条款。努力筛选适合托管公司的客户是维护托管环境安全的另一种方式。总体而言，面向客户团队的培训计划可以减少问题客户的数量，并在客户遇到问题时提供解决问题的建议。

### 4.5 在网络边缘预防滥用

#### 4.5.1 考虑基于硬件的入侵检测系统（IDS）

在最高层面上，M3AAWG 建议探索网络上的入侵检测保护措施。这些系统有助于为攻击做好准备并进行应对。

#### 4.5.2 使用基于软件的安全扫描和防火墙

自动化和可配置的 Web 应用程序安全和渗透测试工具可用于模拟真实世界的黑客技术和攻击。这使公司能够分析复杂的 Web 应用程序和服务的安全漏洞。至少，每个网络都需要基于硬件或软件的防火墙。保护单个网络和计算机还应增设软件层防火墙。

#### 4.5.3 推广使用 Web 应用程序防火墙

托管服务商应鼓励其托管客户使用 Web 应用程序防火墙（WAF），如 ModSecurity。管理型服务商还应考虑在其客户服务器上管理一组核心 WAF 规则。

#### 4.5.4 为高价值客户实施分级权限分配

新账户的访问权限应受限制。经验丰富、值得信赖的账户应随着其在系统内的驻留时间和声誉增长逐渐获得更广泛的访问权限。

可限制的访问项目包括：

* API 访问
* 服务器创建
* 新域名创建
* 带宽增加

访问权限不应授予大多数客户。可保留给满足以下条件的客户：

* 主动防范任何潜在滥用
* 已托管较长时间（超过 12 个月）
* 对公司请求响应迅速

与任何权限一样，这些权利必须在客户（即使此前信誉良好）多次滥用或对公司查询不作回应的情况下予以撤销。

#### 4.5.5 通过合同保护安全

托管服务商必须要求客户在其网络内及所提供服务中、在消耗服务商资源时维护安全环境。这些要求必须在服务开通前告知客户，并构成合同义务的一部分。客户必须有合同义务向服务商通知违规和问题。

应鼓励客户定期备份数据并安全地维护这些备份。备份使客户能够在遭受入侵时将服务器恢复到先前的已知良好状态。

#### 4.5.6 最大化客户联系渠道，保护客户身份

托管服务商应维护更新且多样的客户联系渠道，如电子邮件地址、电话号码、聊天账号和客户门户，以便发送通知。

为保护服务商自身安全，审查过程应包括提供完整的客户身份信息。此外，客户身份档案应作为服务商与客户之间持续通信安全的一部分。

各服务商采用的方法（客户也可建议自己的认证方式）：

* 唯一口令短语
* PIN 码
* 支付所用信用卡的最后四位数字
* 账户所有者必须将特定个人列为已获批的联系人

#### 4.5.7 强化客户密码

托管服务商必须要求使用复杂密码，并应提供双因素认证。密码应在相对较短的时间间隔内定期过期。

托管服务商应为每个客户维护密码/策略历史记录。

#### 4.5.8 在 IPv6 网络上使用最佳实践

IPv6 提供如此多的地址，以至于没有必要——也没有理由——在多个客户之间共享单个 IP 地址。最佳实践是为每个客户分配一个独立的 /64 地址空间。即使在最小的物理共享系统上，每个客户和每个网站都应具有唯一的地址。这使得追踪滥用来源更加容易，使滥用的接收方能够阻止违规客户而不影响同一主机上的其他所有人，并在需要时更容易地暂停和恢复服务。

#### 4.5.9 安全至高无上

托管服务商必须维护强大的内部安全实践和系统。如果恶意行为者能够猜到服务商员工使用的密码，上述所有推荐措施都毫无意义。托管服务商应遵循 PCI 合规标准。

## 五、检测与识别

M3AAWG 推荐以下实践以防止入侵和检测滥用活动：

### 5.1 使用保密客户标识符

托管公司应为每个客户创建唯一的标识符。此标识符仅对托管公司可见，对外部方不可识别。这既保护了客户身份的隐私，又为托管公司提供了一种简单有效的客户识别方式。

### 5.2 建立域名角色账户

必须为网络上配置的每个域和客户域设置 RFC 指定的角色账户和常见实践邮箱。

| 角色账户 | 托管服务商 | 有邮件的客户 |
| --- | --- | --- |
| postmaster@ | 必须 | 必须 |
| abuse@ | 必须 | 必须 |
| hostmaster@ | 必须 | — |
| noc@ | 必须 | — |
| legal@ / copyright@ | 必须 | — |

### 5.3 维护准确的 SWIP 和 IP WHOIS 记录

托管公司应维护其区域互联网注册机构（RIR）中关于 IP 地址分配的清晰准确记录，包括大于 /27 的子分配。这些 WHOIS 记录应包含用于滥用报告的功能性角色账户。

### 5.4 设置内部遥测以报告网络状态

* 网络自扫描
* 流量分析
* 出站垃圾邮件过滤器监控

### 5.5 使社区滥用报告简单直接

托管服务商必须提供渠道供社区成员提交有关其所感知的来自该网络的滥用报告。服务商随后必须确认收到这些报告并采取适当行动。

托管服务商应维护冗余的通信渠道以应对某一渠道的故障：

* 电子邮件
* 电话
* 即时消息（聊天）
* 工单系统（见附录四）
* 网站状态报告
* 社交媒体存在

报告渠道应持续监控。问题应根据第六节中的系统滥用投诉优先级表进行处理。未能处理滥用报告可能导致问题广泛传播，对服务商及其终端用户客户造成负面后果。

### 5.6 及时响应投诉

单个提交应收到自动确认（AUTO-ACK）消息，该消息应具有足够的特异性以与投诉方所做的其他提交区分开来。应包含原始投诉内容、原始工单编号以及任何其他可让用户确信投诉已收到并正在处理的信息。

* 可维护一个静默提交地址，用于批量提交和不需要此类确认的用户。
* 也可为批量提交维护 API 接口。

另见第六节修复与处置部分。

### 5.7 考虑指定可信举报人

投诉提交者可能被认定为高质量或高优先级来源，这些来源可以是内部的也可以是外部的。应提供优先通道式的服务，同时保持指定的优先级级别。

例如，一个广泛使用的 DNSBL（域名系统黑名单）的联系人可被指定为适当的优先级举报人——尽管来自该来源的垃圾邮件投诉显然仍不如同时发生的 DDoS 问题重要。

### 5.8 设置反馈循环（FBL）和自动化报告

**消费 FBL 数据**：注册 FBL 有助于服务商避免 DNSBL 列表收录、限制声誉损害，并使团队能够主动处理滥用和被滥用（已入侵）的客户。

**为具有入站消息基础设施的服务商设置 FBL**：服务商可能希望发布自己的 FBL——业内已有先例——作为报告并因此减少滥用量的一种方式。

**自动化报告**：自动化报告应按照 RFC 5965 和 RFC 6650 进行。

## 六、修复与处置

处置优先级为托管公司和客户提供解决问题的指南。关于投诉优先级的推荐还需考虑滥用的严重性和紧急性以及特定问题的范围。此外，报告来源和对托管公司及客户声誉的损害程度也必须纳入考量。一场大规模的垃圾邮件活动可能比一个休眠僵尸网络的 C&C 控制端优先级更高。对于可能改变特定服务商或客户优先级水平的问题，必须进行逐案评估。

### 系统滥用投诉优先级

| 优先级 | 级别 | 滥用类型 |
| --- | --- | --- |
| 关键（Critical） | P0 | 儿童剥削、攻击性或有害内容、公司数据盗窃 |
| 高（High） | P1 | 僵尸网络 C&C、DDoS、网络上数据盗窃、来自网络的数据盗窃 |
| 中（Medium） | P2 | 恶意软件下载、钓鱼数据收集、钓鱼网站托管、字典/暴力攻击、客户侧数据盗窃 |
| 低（Low） | P3 | 垃圾邮件、控制面板入侵、SSH 转发、网络内垃圾广告推广、垃圾广告支撑网络/黑客破解 |
| 很低（Very Low） | P4 | 远程文件注入、网页涂改、可利用服务、端口扫描、评论垃圾 |
| 按情况 | \* | 版权和商标问题——优先级因位置和服务商而异。例如在北美，由于 DMCA 安全港要求，通常为 P1 或 P2；在没有此类法律要求的地区可能优先级较低。 |

### 6.1 迅速响应高关注度/高优先级问题

托管公司收到的大多数投诉仅需要确认收据。然而，某些情况——如高关注度投诉、下架请求和黑名单移除——需要额外的回应。客户或举报机构应被初步联系，告知问题正在处理中。问题解决时应再次联系他们。只有在存在遗留或异常问题时，才需要进行多次通信。

### 6.2 在行业或公司范围内事件发生时主动沟通

在发生可能危及多个客户或特定客户群体的严重入侵或漏洞时，应制定沟通计划，使他们了解问题，并提供问题解决的一般说明。这些通信必须及时发送。此外，支持人员应了解问题，并具备为需要帮助的客户解决问题的适当说明。

### 6.3 有效处理问题客户

1. 确认投诉的有效性。
2. 通知客户存在入侵。包括经过审查的可帮助解决问题的说明。
3. 向客户提供相关的条款与条件（T&C）和/或任何可能被违反并导致违规通知或服务暂停的适用政府法规。通过这样做，与客户的协议得以维持。通知客户保护了托管公司免受潜在的客户或外部投诉方的诉讼风险。
4. 给予客户解决问题的时间——或者如果已有协议，则允许服务商自行解决问题的时间。
5. 确认投诉已解决。
6. 关闭事件。如有必要，通知举报方问题已解决。

### 6.4 对不作回应的客户暂停服务

如果客户已被入侵或从事危害托管服务商网络的活动，且不采取行动解决问题，服务商必须有能力移除服务或在终止合同前予以关停。这可以采取显示暂停网页（要求所有者联系托管服务商）的形式，或关闭托管环境关键方面的能力。例如，反复发送垃圾邮件的违规者的电子邮件发送能力可被暂停一段时间。

### 6.5 终止不作回应的客户

当一个不作回应的客户持续在服务商网络上制造滥用时，必须终止关系以保护服务商及其客户。

决定终止时需考虑的因素：

* 与托管公司合作的时间长度
* 账户规模
* 违规的类型和数量
* 解决违规的时间和响应度
* 对面向客户员工有攻击行为的客户
* 账户的服务级别

终止后应执行的操作：

* 设定客户取回数据的时间框架
* 明确告知已不再欢迎其使用托管公司服务
* 通知支持、销售和计费部门该账户已终止
* 在时间框架结束时确认账户已被移除

### 6.6 欺诈账户的特殊处理

上述许多措施不适用于被认定为欺诈的账户。例如，欺诈账户不应被允许取回其数据。必须注意不要惊动不法分子，以免他们获悉正在采取的保障网络安全的行动。

## 七、国内合规补充

以下内容是对原文的补充，适用于中国境内从事 IDC 和云服务的运营者。

### 7.1 法律法规要求

* **《网络安全法》**（2017）：要求网络运营者采取技术措施防范网络滥用和恶意攻击，留存相关日志不少于六个月，并建立网络安全事件应急预案。
* **《反恐怖主义法》**：要求电信业务经营者和互联网服务提供者落实技术防范措施，发现含有恐怖主义、极端主义内容的信息应立即停止传输并报告。
* **《互联网信息服务管理办法》**：明确互联网信息服务提供者的内容管理责任，发现违法信息应当立即停止传输并报告。
* **《通信网络安全防护管理办法》**（工信部令第 11 号）：要求通信网络运行单位进行安全风险评估和等级保护。
* **《关于加强网络信息保护的决定》**：要求收集和使用用户信息须经用户同意，并采取安全措施防止信息泄露。
* **《即时通信工具公众信息服务发展管理暂行规定》**：涉及即时通信服务中的信息内容管理。

### 7.2 垃圾邮件与 12321 网络举报

* **12321 网络不良与垃圾信息举报受理中心**：工信部委托中国互联网协会设立的举报机构，受理垃圾短信、垃圾邮件、不良网站等举报。托管和云服务商应建立与 12321 对接的投诉处理机制，及时处理转办的滥用投诉。
* **CNNIC（中国互联网络信息中心）**：负责 .CN 域名注册管理，对域名滥用（如钓鱼域名）实施处置。服务商应配合 CNNIC 的域名处置要求。
* **《互联网电子邮件服务管理办法》**（信息产业部令第 38 号）：规定电子邮件服务提供者的垃圾邮件过滤、用户举报处理、发送限制等义务。
* **《通信短信息服务管理规定》**：规范商业短信息发送行为，涉及 IDC 下客户群发短信的合规要求。

### 7.3 等级保护（等保 2.0）对接

IDC 和云服务商应按照《信息安全技术 网络安全等级保护基本要求》（GB/T 22239-2019）落实安全保护措施，包括：

* 安全通信网络：网络边界防护、访问控制
* 安全区域边界：入侵检测、恶意代码防范
* 安全计算环境：操作系统安全、应用安全
* 安全管理中心：集中日志审计、安全事件管理

### 7.4 个人信息的保护

根据《个人信息保护法》（2021），处理用户个人信息应当遵循最小必要原则。托管和云服务商在处理滥用投诉时涉及用户信息的，应依法合规使用。

### 7.5 跨境数据传输

云服务商涉及跨境提供服务的，应遵守《数据安全法》关于数据出境安全管理的要求。

## 附录一：标准术语表

如无特别说明，以下术语源自 RFC 5598。

滥用报告（Abuse Report）
:   泛指任何恶意软件、钓鱼或垃圾邮件报告的统称。

服务器 / 盒子（Box）
:   托管服务商和客户用于运行各种程序的物理硬件。

DMCA
:   1998 年《数字千年版权法案》，保护版权持有人免受未经授权的电子传播。根据该法案，美国互联网服务提供商收到版权持有人关于其客户侵犯版权的通知。详见美国版权局报告。

电子邮件服务提供商（ESP）
:   提供批量邮件发送服务的公司。

终端用户（End User）
:   使用托管服务商服务的客户的客户。

反馈循环（FBL）
:   邮箱服务商用于与合格的合法发件人共享被举报为垃圾邮件的消息副本的系统。系统旨在使发件人能够识别和解决引起投诉的问题。

硬退回（Hard Bounce）
:   接收 MTA 指示由于永久性故障（电子邮件地址不存在、域名不存在）而无法投递邮件。

邮箱服务商（Mailbox Provider）
:   向终端用户提供邮箱的公司，可能同时提供互联网接入服务。

消息滥用投诉/报告
:   消息的收件人对某消息提出投诉或报告为滥用的行为。最常见的途径是点击网页界面中的垃圾邮件按钮。也可通过向邮箱服务商的支持或滥用部门提交工单、发送邮件或拨打电话进行投诉。

选择加入（Opt-in）
:   收件人表示希望收到来自此发件人的消息。

选择退出（Opt-out）
:   收件人表示不希望收到来自此发件人的消息。

接收 MTA
:   邮箱服务商用于接收邮件的邮件传输代理。

区域互联网注册机构（RIR）
:   负责分配 IP 地址的五个区域组织之一：AfriNIC（非洲）、LACNIC（拉丁美洲）、ARIN（北美和南极洲）、RIPE（欧洲）和 APNIC（亚太区）。所有上述机构提供基于发送者 IP 地址的来源查询表。

发件人（Sender）
:   电子邮件的来源或起源。既可以指控制发送 MTA 的 ESP，也可以指负责消息内容的品牌或公司。

发送 MTA
:   发件人用于发送邮件的邮件传输代理。

共享 IP
:   许多不同的发件人/品牌/ESP 客户同时从该 IP 发信的 IP 地址。通常与所属的 ESP 关联，而非其上的某个品牌。

## 附录三：关于数据安全

从事数据存储和订阅用户电子邮件地址或其他个人身份信息管理的专业人员，强烈建议维护全面的安全计划，利用行业标准的最佳实践来实现其环境和应用程序的安全。详细建议超出本文范围。此外，大多数国家都有服务商必须遵守的法律要求。

作为起点，作者建议搜索开放 Web 应用程序安全项目（OWASP）和计算机安全培训组织 SANS 的更多信息，它们提供了大量关于网络安全和数据安全风险及建议的信息。

此外，一些成员建议遵循 ISO/IEC 27002:2013 控制措施——特别是该国际标准中访问控制、通信与运营管理以及信息安全事件管理领域的控制要求——作为全面安全计划的合适基础。

M3AAWG 强烈建议将数据安全作为制定数据收集和存储流程的首要考量因素。正如罪犯抢劫银行因为那里有钱，网络犯罪分子也将电子邮件服务商和其他消费者数据在线管理者视为获取电子邮件地址等数据以用于恶意目的的目标。同样，不要因为托管服务商的服务或软件仅存储电子邮件地址就认为它不太可能成为目标。数据对其所有者和恶意行为者同样有价值。确保数据得到妥善保管、不落入犯罪分子之手至关重要。

## 附录四：工单系统

工单系统对于维护适当的工作流程和跟踪当前问题至关重要。无论托管服务商运营如何组织，工单系统都是关键的。在大多数情况下，该系统不仅由滥用团队使用。服务商需要一个能够区分各部门并在各部门内创建子组的系统。系统应在工单进入时应用日期和时间戳。随着报告数量的增长，服务商很可能需要更多的人来审查这些报告。将报告方便地归入工单系统意味着团队无需在多个位置查找。

托管服务商的系统还必须为非客户提供报告接口。这可以是一个简单的网页，使他们能够直接将垃圾邮件或钓鱼等问题报告给服务商的滥用团队。系统随后应自动创建工单。

服务商还需要能够将电子邮件报告作为工单拉入系统。订阅反馈列表使服务商能够将这些报告纳入其工单系统。应设置系统使这些工单被分配给服务商系统中的正确区域。一旦设置反馈循环区域，可以为 AOL、Comcast、Google、Spamhaus 等创建子文件夹。不同的区域使报告更容易被优先处理。

系统必须可搜索。通常会在同一时间或不同时间收到来自不同来源的关于同一问题的多个报告。一次性收集所有报告的能力可防止团队被大量重复工单淹没，从而避免浪费时间去处理重复报告。

目前，恶意软件报告标准团队正在考虑引入举报人信誉机制——使已知的良好行为者（如 Spamhaus）获得优先处理，而来自未知方的报告则被评定为较低优先级。如果此机制被采纳，托管服务商将需要相应调整其工单系统。

## 结论

这些最佳通用实践旨在为托管商、DNS 和域名注册服务商提供必要的建议，以保持持续警惕、保护其系统免受入侵。实施这些实践将惠及整个在线社区——通过预防滥用，同时帮助托管服务商避免代价高昂且耗时的问题。
